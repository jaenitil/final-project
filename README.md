# Оправа — каталог ювелірних виробів (React)

Фінальний проєкт курсу. Каталог виробів приватної ювелірної майстерні: перегляд
виробів, фільтр за ціною, колекції, реєстрація/вхід, обране, кабінет
користувача.

## Стек

- React 18 + Vite
- React Router — навігація, приватні маршрути
- Redux Toolkit — глобальний стан (auth, pieces, favorites, collections)
- Axios — основний HTTP-клієнт, з інтерцептором, що сам додає JWT-токен
- Нативний `fetch()` + async/await — навмисно використаний окремо у
  `src/api/collectionsApi.js`, щоб показати обидва підходи до запитів
- Formik + Yup — усі форми (логін, реєстрація, відновлення пароля, профіль,
  додавання виробу) з валідацією

## Розділи сайту

- **Каталог** (`/`) — вироби з відсіками за типом, пошуком за назвою/описом,
  фільтром за колекцією та ціною
- **Колекції** (`/collections`)
- **Про нас** (`/about`) — історія майстерні, фото (`public/images/about/`)
- **Контакти** (`/contacts`)
- **Доставка та замовлення** (`/delivery`) — у футері
- **Умови користування** (`/terms`) — публічна оферта, у футері
- **Обране / Кабінет / Додати виріб** — тільки для залогінених

Тексти на сторінках "Про нас" / "Контакти" / "Доставка" / "Умови" — це
шаблон із позначками `[тут вписати...]`, заміни на реальні дані майстерні.

## Як запустити

```bash
npm install
npm run dev
```

Відкриється http://localhost:5173

API вже прописаний у `.env` (`VITE_API_BASE_URL`), нічого додатково
налаштовувати не треба. Якщо адреса бекенду зміниться — постав нову там.

## Структура проєкту

```
src/
  api/          — axios-інстанс і функції запитів до кожного розділу API
  app/store.js  — конфігурація Redux-стору
  features/     — Redux-слайси (auth, pieces, favorites, collections)
  hooks/        — useAuth, useDebounce
  routes/       — ProtectedRoute (захист приватних сторінок)
  components/   — Header, Footer, PieceCard, Loader
  pages/        — сторінки застосунку
```

## Наповнити каталог тестовими виробами

У каталозі за замовчуванням порожньо (чи мало даних), бо це спільний
навчальний бекенд. Щоб додати 12 готових виробів (кільця, сережки, кулони,
браслети — з описом і фото-заглушкою) та 4 колекції:

```bash
# спершу зареєструйся через сам застосунок (сторінка /register),
# потім:
node scripts/seed.mjs твій@email.com твійПароль
```

Скрипт логіниться під твоїм акаунтом і додає дані напряму через
`POST /api/manufactures` та `POST /api/cars` — тобто через справжній API, а
не хардкод. Фото — охайні кольорові заглушки (placehold.co) з підписом типу
виробу; коли будуть реальні фото прикрас — просто заміни посилання в полі
`image` у масиві `PIECES` всередині `scripts/seed.mjs` (або онови вже
створені записи через форму редагування, якщо додаси її).

Відсіки-вкладки на каталозі (Каблучки / Сережки / Кулони / Браслети)
визначаються автоматично за ключовим словом у назві виробу (див.
`src/utils/pieceType.js`) — бекенд не має окремого поля "тип", тому кожна
нова назва має містити одне зі слів: каблучка/перстень, сережки,
кулон/підвіска/намисто, браслет.

## Як API мапиться на UI

Бекенд (`frontend53.somee.com`) — спільний навчальний API з різними
сутностями (Book, Car, Event, Task тощо). Для теми "ювелірна майстерня"
найкраще підійшла сутність **Car**, тому що структурно вона максимально
близька до ювелірного виробу:

| Поле в API (Car)  | Що показуємо в інтерфейсі         |
| ------------------ | ---------------------------------- |
| `name`              | назва виробу                       |
| `price`              | ціна, грн                          |
| `color`              | колір металу/каменя                |
| `year`               | рік колекції                       |
| `volume`             | вага, г                            |
| `image`              | фото                                |
| `description`        | опис                                |
| `manufactureId`       | звʼязок із колекцією (Manufacture) |

`Manufacture` → **«Колекція»**, `FavoriteCar` → **«Обране»**. У самому
інтерфейсі ніде не видно слова "машина" — це чиста презентаційна мапа поверх
готового бекенду.

## ⚠️ Важливо перевірити перед захистом

Swagger цього бекенду описує лише `200 OK` без схеми тіла відповіді — тобто
я **не можу зі 100% точністю знати**, які саме поля повертає сервер у
відповідь на логін, реєстрацію, `GET /cars` тощо. Код написано захисно
(перевіряє кілька можливих варіантів назв полів: `token`/`accessToken`,
`items`/`data` тощо), але раджу зробити один прогін і звірити:

1. Відкрий DevTools → Network, залогінься.
2. Подивись відповідь `/api/auth/login` — переконайся, що токен дістається
   правильно в `src/api/authApi.js` (функція `loginRequest`).
3. Так само перевір форму відповіді `GET /api/cars` — чи це просто масив, чи
   обʼєкт з пагінацією (`{ items: [...], total: ... }`). Якщо структура інша —
   поправ парсинг у `src/features/pieces/piecesSlice.js` (шукай
   `Array.isArray(action.payload) ? ... : action.payload?.items ...`).
4. Якщо `POST /api/auth/register` вимагає `callbackUrl` для підтвердження
   email — можна лишити порожнім, або вказати будь-який URL (наприклад,
   `http://localhost:5173/login`).

Якщо в браузері під час розробки запити падають з CORS-помилкою — це
налаштування самого бекенду (somee.com), тут з боку фронтенду виправити
нічого не можна; напиши викладачу/адміну бекенду.

## Що можна доробити (якщо лишиться час)

- Редагування/видалення виробів (`updatePiece`, `deletePiece` вже готові в
  `piecesApi.js`, залишилось додати кнопки в UI)
- Підтвердження email після реєстрації (`GET /api/auth/confirmEmail`)
- Аватар користувача (`PATCH /api/user/avatar`, multipart/form-data)
